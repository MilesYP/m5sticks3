# CC1101 SPI 讀寫可靠性實測（RF Pack S3）

- 日期：2026-11-17
- 工具：`rssi-test/` v6.4／v6.5（自有韌體，只接收不發射）
- 環境：StickS3 + RF Pack S3、`espressif32@6.12.0`（Arduino 2.0.17／ESP-IDF 4.4）、SmartRC-CC1101-Driver-Lib `7bba5217`、`Init()` 只呼叫一次、SPI2（SCK 5／MISO 4／MOSI 6／CS 2／GDO0 3）
- 電量 100%、完整斷電後重開、機器靜置不碰

## 1. 結論
| 項目 | 結果 |
| :-- | :-- |
| 單筆讀取（`SpiReadReg`／`SpiReadStatus`） | **穩定約 0.5% 回傳錯值**（12 次量測，每 200 筆幾乎都恰好錯 1 筆），IDLE 與 RX 相同 |
| 連讀到兩次相同才採用 | **不可靠**：12 次量測中 2 次出現「兩筆一致但值是錯的」（1/200 與 **14/200**）→ 錯誤會成叢發生 |
| 建議讀法 | **多數決（至少 3 筆）＋ 關鍵時機用 `VERSION`＝`0x14` 做語意檢查** |
| 寫入後驗證並重試 | 1～2 次成功（IDLE 與 RX 皆可） |
| 高強度連續存取之後 | 接下來的讀取卡約 2 秒（逾時 1 秒 × 2）後**自行恢復** |
| 兩輪高強度存取零間隔連跑 | **完全鎖死、不自行恢復**，要重置板子 |
| 接收功能 | 正常（315.00 MHz −16 dBm、333.00 MHz −18 dBm） |

硬體是否該換貨：**無法由單一片板子判定**。錯誤形態規律、可用重試完全修正、接收正常，偏向匯流排／驅動時序的邊際問題而非晶片損壞；但不能排除本片的訊號緩衝電路較差。

## 2. 錯值的形態
實際出現過的錯值：`00`、`03`、`07`、`08`、`0F`、`1F`、`20`、`34`、`7C`、`87`、`8F`、`C3`、`C7`、`E1`、`E3`、`F0`、`F8`。

其中 `0x` 與 `1x` 這一類符合 **CC1101 狀態位元組**的格式（bit6-4 ＝ 晶片狀態、bit3-0 ＝ FIFO 位元組數；IDLE 時高位元為 `000`→`0x`，RX 時為 `001`→`1x`）。CC1101 的每次交易第一個回傳位元組是狀態位元組、第二個才是資料，所以這像是**資料位元組被吃掉或錯位一個位元組**，屬時序問題，不是晶片回報了錯誤內容。

`C3`／`C7`／`F8`／`E1`／`E3` 這類高位元為 1 的值，對應 CHIP_RDY＝1（晶片未就緒）或 RXFIFO_OVERFLOW 等狀態，同樣是狀態位元組而非資料。

**切換晶片狀態（SIDLE／SRX）後的第一筆交易特別容易錯**：多次測試的第一筆常是 `0F`、`07`、`03`、`08`、`1F`。

**錯誤不是獨立隨機的**：若每筆獨立錯 0.5%，連兩筆錯成同一個值的機率約 0.0025%，但實測出現 14/200（7%）→ 錯誤會成叢出現、同一個錯值會連續重複，所以「連讀兩次相同」這種防錯法會被騙過。

## 3. 「完全停止回應」的觸發條件
症狀：`checkMISO()` 持續印 `Fail checking MISO pin`，每筆讀取卡滿 1 秒逾時，不會自行恢復；重置板子後恢復正常。

| 情境 | 結果 |
| :-- | :-- |
| MONITOR 每 2 ms 讀一次 RSSI，連續 5 分鐘以上 | 正常，0 次 |
| MONITOR 每 10 秒連讀 20＋筆暫存器，共 3 分鐘 | 約每 30 秒卡約 2 秒，自行恢復（3 次） |
| 跑一輪 SPI 測試（約 900 筆交易） | 正常跑完 |
| 一輪測試結束後恢復 RSSI 取樣 | 下一筆讀取卡 2022 ms（逾時 1011 ms × 2）後自行恢復；6 輪測試中發生 2 次 |
| 連續跑 6 輪測試，每輪間隔數秒 | 6 輪全部正常跑完，無永久鎖死 |
| **連續跑第二輪，中間無間隔（連按或長按 B）** | **立刻完全停止回應，不恢復** |
| 間隔約 2 秒再跑第二輪 | 正常跑完 |

→ 觸發條件是**短時間內大量連續交易**，而不是累積運轉時間、電量或外部訊號。

## 4. 韌體規則（已寫入 `CLAUDE.md` 鐵則五第 7 點）
1. 讀暫存器用**多數決（至少 3 筆，無多數就擴大到 9 筆）**，不要只用「連讀兩次相同」。
2. 切換狀態或改完設定後，先用 `VERSION`＝`0x14` 做語意檢查，通過才信任其他讀值。
3. 寫暫存器一律寫完驗證，不符就重寫。
4. **不要用函式庫的 read-modify-write 函式改位元欄位**（`setModulation`／`setPktFormat`／`setRxBW`／`setCCMode` 內部都先 `Split_*()` 讀回再寫回，讀錯就把垃圾寫進晶片）。要改就自己算出完整位元組整顆寫入並驗證。
5. 不要在任何狀態做 burst 式連續讀取；RSSI 取樣維持間隔（實測 2 ms 可行）。
6. 高強度存取之間至少留 2 秒。

## 5. 相關觀察
- 先前 `[regs]` 讀到 `PKTCTRL0=3F`（預期 `32`）、`FREQ2` 每次不同，都可由上述讀取錯誤解釋。`PKTCTRL0` 的異常值更可能是第 3 點的 read-modify-write 把錯值寫了進去。
- v5（階段四）在 IDLE 下 400 次讀取 0 錯誤，是因為當時未在 RX、且未做更高強度的壓力測試；不代表本片沒有這個問題。
- RSSI 量測值大致可信（讀 RSSI 本來就用連讀確認），但依第 2 節的叢發特性，個別讀值仍可能錯；統計值（min／avg／max 取自數千筆）不受影響。
- 正常 MONITOR 運轉時 `badread`（MARCSTATE 單次讀值不一致）約每秒 +1，與 0.5% 錯誤率一致。
- 一次 hang 之後的 `[regs]` 內容大量錯誤（`MDMCFG4=07`、`PKTCTRL0=07`、`FREND1=03`、`TEST0=07`），印證「剛從卡住恢復時讀值特別不可信」。

## 6. 這是正常的嗎
乾淨的 SPI 匯流排應該幾乎零錯誤，0.5% 的穩定錯誤率與會自行恢復的 2 秒鎖死**都不是正常表現**。但錯誤形態規律、重試可用、接收功能正常，仍無法由單一片板子分辨是「本片瑕疵」或「RF Pack S3 ＋ 這顆驅動的共同特性」。已請 PINGEQUA 用樣品跑同一支測試對照。
